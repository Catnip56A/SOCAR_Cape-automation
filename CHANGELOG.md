## [1.0.21] - 2026-10-13
### Added
- **MR vs CTR Statistics: the Include scaffold box is gone** (scaffold only exists in the CTR Generator); in Document price the toolbar says "Scaffold: not included here" instead, with a tooltip explaining it (`StatsPanel(show_scaffold=False)`). The Generator keeps the option.
- **Statistics: Document costs / Document price (MR vs CTR Statistics tab and the CTR Generator's statistics box).** A two-button toggle in the toolbar. **Document costs** is what the statistics always showed (SAGE expected unit cost × quantity). **Document price** shows what the documents bill: **quantity × rate**, **× days for equipment and scaffold**. The rate is looked up the way the CTR Generator does it, with no fallback between the two: **equipment from the USD Pricebook** (through the Combined DB's equipment-names sheet, the normal `-NOR` rate preferred, a bridge code tagged non-recharge = 0), **consumables from SAGE** (first row per product, as before). A **Non-Rechargeable** line is billed at **0**. In the Generator each line keeps **its own rate cell and days** (what the CTR would carry; a blank cell is never filled from SAGE behind its back); in the MR vs CTR tab days are **typed by you** (double-click the *Days* cell of a red row; one value per Stock Code, saved with the comparison). Nothing is assumed: a line with no quantity, no rate or (equipment) no days is **not counted**, shown in red, and the yellow banner counts them. A Stock Code no CTR section names is treated as equipment when the equipment lookups know it, else as a consumable. The panel gains a **Description** column (the line's own description, else SAGE's name) and a **Days** column; the *Non ÷ Rech* column is hidden in the price view (non-rechargeable is 0). `cost_stats.price_view`, `equip_rate_map`, `price_report_frames`, new row columns `description / kind / rate / days / scaffold / own_rate`; `StatsPanel.set_mode`, `days_changed`, `view_changed` (`stats_view.py`).
- **Include scaffold** (price view; **off by default**). Scaffold is rechargeable equipment: tonnage × rate/day × days, from the Generator's scaffold line. It has no SAGE cost, so it never appears in Document costs.
- **With markup** (price view, **CTR Generator only**): adds the Generator's **Markup Rate** (6.5 % default) to **consumables**. The MR vs CTR tab has no markup option and prices without it.
- **Price totals in the CTR Generator** (under the statistics list): per category and per currency — **AZN: Manpower, Transport (Third Party Activities), AZN total; USD: Equipment, Consumables, USD total**. AZN and USD are never added together. The figures are the tables' own Total cells (what a generated CTR carries); transport at a quantity of 0 or less counts 0; a row with a missing required value is left out as Generate leaves it out, and the box says how many (*“n line(s) not priced”*). Scaffold is added to Equipment only when *Include scaffold* is on. `CTRGeneratorWidget.price_totals`, `_refresh_price_totals` (`ctr_tools/window.py`).
- **USD Pricebook and Combined DB fields in the MR vs CTR tab** (one line under the SAGE Export field), shared with the CTR Generator tab like the SAGE Export: setting one sets the other, and changing them after a Compare recalculates the equipment rates. A banner in the price view says when the USD Pricebook is not set or not found. `MainWindow._build_pricebook_row`, `_on_price_source_edited` (`app.py`); `usd_pricebook_path_changed`, `combined_db_path_changed`, `loaded_usd_df`, `loaded_names_df` (`ctr_tools/window.py`).
- **Settings → Rechargeability choices: Edit…** The list of per-Stock-Code choices made in the Disparities window (*Document is right* / *SAGE is right*) can now be **edited in Settings**: add a code to settle it before it ever shows up, change a choice, or remove one (*Edit…* opens a table; *Reset…* and *Restore…* work as before). It is the **same one list** the Disparities window fills in and that both statistics lists share. `_ChoicesDialog`, `SettingsTab._edit_choices` (`common/settings_view.py`).
- **Settings → Statistics defaults**: which view starts first (costs or price), whether scaffold is included, and whether the price view includes the markup. They set the starting position of the toggles; the toggles can still be changed in the tabs.
- **Excel**: the MR vs CTR report and the Generator's *Save statistics (Excel)* get **Price Statistics** and **Price Items** sheets next to the Cost sheets (always everything, the scaffold and markup toggles apply); the item sheets gain a **Description** column; The Generator's *Info* sheet explains the price basis. Saved comparisons keep the price inputs and days (older saves load, but show no rate in the price view).
- Tests: `tests/test_price_stats.py` (price rules, equipment lookup, editable choices, toggles and defaults, totals, the MR vs CTR window and both Excel files).

## [1.0.20] - 2026-10-13
### Added
- **Settings: Restore… and tidy backups.** Each saved list (aliases, renames, presets) has a **Restore…** button (it shows how many backups exist) that lists the backups — date and number of entries, unreadable ones greyed out — and brings the chosen one back; the list as it is now is backed up first, so a restore can be undone too. Only the **newest 5** backups per list are kept (older `.bak-…` files used to pile up forever). A folder that cannot be written to is reported (*“The folder … cannot be written to”*) and nothing is changed, for both Reset and Restore. `backups_for`, `copy_backup`, `prune_backups`, `check_writable`, `_RestoreDialog`, `SettingsTab._restore` (`settings_view.py`).
- **Offscreen tests kept in the repo** (`tests/`, run with `python tests/run_all.py`; see `tests/README.md`): 40 tests for the Generator rules, quantities, Encoding, Go to value, statistics navigation, Ctrl+F, hover text and Settings. They run in a temporary sandbox and never touch the real data folders or `TEST_Files/**/Output`.
- **Disparities between the documents and SAGE (MR vs CTR Statistics tab and the CTR Generator's cost statistics).** A **Disparities** button with a red exclamation mark appears in the statistics toolbar when a Stock Code is **Rechargeable in the document but Non-Rechargeable in SAGE (or the other way round)** — the document's side is the MR *Rechargeable* column, the CTR *Rate* column, or the Generator's rate/price cell; SAGE's side is its own tag (`analysis_b`, first row per product). It shows the number of Stock Codes and opens a list (Side, Document, Stock Code, **Item** — SAGE's description of the code, also shown at the top of each *Choose source…* menu — what the document says, what SAGE says, what you chose, how many lines). Until a source is chosen the item is **not counted** (red in the tree, counted in the yellow banner) and the **CTR Generator will not generate**. **Choose source…** on each line lets you decide, per Stock Code, whether the **document** or **SAGE** is right (*Clear my choice* undoes it; a tick box also lists the ones already chosen). A chosen item is counted with the chosen rechargeability. The choices are **one list for the whole app** — a choice made in the MR vs CTR list shows in the Generator's list and vice versa — and are **remembered between runs** (`source_choices.json` in the data folder; Settings shows how many, with Reset / Restore). In the Generator, choosing **SAGE** makes the Equipment / Consumables lines of that code say what SAGE says: SAGE non-rechargeable → the rate/price cell becomes `NONRECHARG`; SAGE rechargeable and the cell is `NONRECHARG` → the cell is emptied (red: a rate or price must be entered, nothing is assumed). Choosing the document changes no cell. A code the document gives no rechargeability for, or that is not in SAGE, is not a disparity. Saved comparisons keep the disparities (older saves load without any); the Excel report gets *“…of which differs from SAGE”*, *“Item (SAGE name)”*, *“Document says”*, *“SAGE says”* and *“Source chosen”*. Only rechargeability is compared. `cost_stats.sage_tag_map`, `DISPARITY`, `CHOICE_SAGE/DOC`, `apply_manual(choices=…)`, `disparities`; `StatsPanel.set_choice/set_choices/choices_changed`, `DisparitiesDialog`, `alert_icon` (`stats_view.py`); `ctr_tools/source_choices.py`; `_apply_all_choices_to_lines`, `_generate` (`ctr_tools/window.py`); `settings_view.py`; `app.py` (the two lists share the choices); `tests/test_disparities.py`. In the test request 11 lines differ, mostly equipment (the CTR's equipment rechargeability comes from the Equipment Names DB, not from SAGE's tag).
- **Repository hygiene: user data stays out of git.** `.gitignore` now ignores CTR presets (`**/ctr_presets*.json`), Inspector snapshots (`logs/snapshots/`), backups (`*.bak-*`) and saved comparisons (`**/Comparisons/`); shipped config files (`template_config.json`, `match_aliases.json`) stay tracked. Task-log backups are kept one per release instead of one per write (`.claude/task_log`).
### Changed
- **CTR Generator: quantities of 0 or less.** **Generate warns** about every quantity that is 0 or negative on a row that goes into the CTR (manpower Num Employees and Hours, equipment, consumables, transport) — the values go in as entered, so check them. **Transport lines with a quantity of 0 or less are hidden in the AZN CTR** (the row is written but hidden — like the labor section's unused rows — so the PDF omits it, and its total cell is 0 so a hidden line never changes the section total, even for a negative quantity); when every transport line is like that, the Third Party section and its Summary line are left out. `_nonpositive_quantities`, `_generate` (`ctr_tools/window.py`); `_write_third_party_section`, `_third_party_qty` (`ctr_tools/builder_azn.py`).
### Fixed
- **Presets: nothing ships any more.** Settings → *Reset* on the CTR presets used to restore a developer preset that was bundled into every build (`ctr_tools/ctr_presets.json`, v1.0.13: a Linux path, a real job scope, fields missing). The file is removed and no longer bundled (`app.spec`); *Reset presets* now empties the list (your own presets are still copied to a `.bak-…` file first). Found by the user testing the reset on Windows.

## [1.0.19] - 2026-10-12
### Added
- **Cost statistics (task MA131) — MR vs CTR Comparator.** A new **Statistics** tab shows how much of the SAGE *expected* cost (`local_expect_cost` × quantity — not what the client is billed) is rechargeable, non-rechargeable or unknown, as amounts and as a percentage of the costed total (so with Unknown items the first two never add up to 100). The tab is a tree: **MR** and **CTR** totals, each expanding to one row per document, each document expanding to its Stock Codes (sort by cost or unit cost, filter by type or rechargeability). It follows the document filter (a row stays when its own document/sheet plus a partner of the same Stock Code on the other side satisfies the expression, as in Matched/Only), has a **Multiply cost by quantity** switch (on by default) and a **Reload statistics** button, and is calculated in the background after every Compare (a parallel job in the Inspector's Tasks; a newer Compare or Reload replaces an older run). A yellow banner that cannot be closed appears only when something is wrong: SAGE not set, still loading, file not found, or Stock Codes not in SAGE. Rechargeability is taken from the documents — MR's `Rechargeable` column, and for the CTR its `Rate` column (a number = rechargeable, `NONRECHARG` = not) — **up for discussion with the department**. New `cost_stats.py` (pure logic), `stats_view.py` (`StatsPanel`, `StatsWorker`); `MainWindow._build_stats_items`, `_start_stats_job`, `_stats_doc_pred` (`app.py`).
- MR vs CTR Statistics: the background job now starts about 0.4 s *after* the comparison is on screen (and at low thread priority), so showing the results never waits for it; the tab says it will appear shortly. ### Fixed
- CTR Tracker: a batch inserting both a currency's brand-new first row for a CTR *and* a new revision of that CTR's other, already-existing currency could compute the exact same target row for both — and since ties were broken by batch submission order, the new-currency row could win the slot that actually belonged to the revision insert, pushing it to the bottom of the whole CTR block instead of landing next to its own currency's row (e.g. a CTR's first USD line, submitted just before a second AZN revision, would shove that AZN revision below the new USD row instead of next to AZN's first). - CTR Tracker: writing two revisions of the same CTR number + currency in one batch (e.g. a corrected line and its original, or a currency's first two revisions together) silently misordered them — the second revision could land *above* the first regardless of which was actually newer, because the row it needed to compare itself against wasn't "real" yet as far as that single write pass could see, and it fell back to a currency-mismatch path that just appends after the last row instead of placing it correctly. Two entries in the same batch for the same CTR number + currency are now detected up front and the later one is skipped with a clear, matchable reason (`IN_BATCH_CONFLICT_MARKER`) instead of being silently misordered — it stays in the batch table (nothing else in the batch is affected) and is automatically retried in a follow-up batch after a 3-second countdown (cancellable), by which point the first revision is genuinely on disk and orders correctly against it. A batch with more than two revisions of the same CTR+currency resolves over several such rounds. `_plan_insertions` (`ctr_tools/tracker_fast.py`); `_maybe_start_retry_countdown`/`_on_retry_tick`/`_cancel_retry_countdown`, `_start_write` (split out of `_write_batch`, `ctr_tools/tracker_window.py`).

- CTR Tracker: a new choice under "Overwrite rows that already have data" — "Overwrite this row" (replaces the matched row's data in place, as before) or "Add as separate revision" (leaves it untouched and writes into a spare pre-created row sharing the same CTR number and currency instead, inserting one via real Excel automation if no spare is available — new `ctr_generator/tracker_xlwings.py`, Windows/macOS with Excel installed only). "Add as separate revision" only actually reaches for a spare/inserted row when the CTR's own revision number genuinely differs from what the matched row already has — writing the *same* revision again (e.g. a corrected value before the revision counter was bumped) overwrites that row in place instead of spawning an extra one for it. When it does insert, the new row is placed in ascending revision order among any other rows already there for that CTR number and currency — between two existing revisions if the new one falls between them, not just appended after whichever row happened to be matched first. `_insertion_row_for_revision` (`ctr_generator/tracker_fast.py`). Once a currency already has at least one revision written, a spare row is only reused for another revision if it's already explicitly labeled with that same currency — an unlabeled blank row is no longer assumed to be fair game, since it's more likely the tracker's own reserved slot for the CTR's *other* currency (its real pairing convention); with no explicitly-matching spare, a fresh row is inserted instead so that reserved slot is left alone. `_row_currency` (`ctr_generator/tracker_fast.py`). Verified end-to-end against the real tracker workbook on Windows, including the row-insertion path specifically: Excel's row-insert doesn't rewrite every formula reference correctly on its own — the row pushed down by an insertion keeps a stale running-count formula pointing above the insertion instead of at the new row, and the sheet's two other row-local formula columns (a source/currency key and a mirrored label) aren't populated on the new row at all — both are now repaired/seeded explicitly, verified correct even across two insertions landing in the same write.
- CTR Tracker: writing a CTR whose number exists in the tracker but has never had a row for that entry's currency — only AZN rows exist and a USD entry comes in, or vice versa — now creates that row instead of failing with "reserved for a different currency", regardless of the Overwrite checkbox (there's nothing existing to protect or overwrite here, just a currency this CTR number hasn't had a row for yet) and regardless of the entry's own revision number (it doesn't need to be a "first" revision to get a row). The new row is inserted right after the last row of whichever currency's block already exists for that CTR number, keeping the two currencies grouped together in the sheet. `_last_row_for_ctr`, and a new `"wrong_currency"` outcome from `_classify_target_row` distinguishing this from a genuine data conflict (`ctr_generator/tracker_fast.py`).

### Fixed
- MR vs CTR Comparator: an MR workbook's hidden/veryHidden template sheets — leftover, never-filled `CH-*`/`NCH-*` pages that a user would never see or fill in in Excel — no longer show up as selectable tables in either the named-range parser or the sheet-based fallback; only sheets actually visible in the workbook are offered. The MR's `Socar-Cape` cover sheet, which duplicates the same request as one big index rather than being a real per-category page, is excluded the same way. `sheet_parser.py`.
- CTR Tracker: writing a batch with more than one entry for the same CTR number (its AZN and USD rows, or two different revisions) only ever wrote the first of them — every other entry for that CTR number came back "no row found", as if the CTR number itself didn't exist, and repeating the write one entry at a time was needed to clear the whole batch. Caused by `_classify_target_row` treating a row another entry in the same batch had already claimed as if it didn't exist at all, instead of just being unavailable as a *target* — the same row's mere existence is what a sibling entry (its other currency, another revision) needs to see to be handled correctly. `_classify_target_row`, `_last_row_for_ctr` (`ctr_generator/tracker_fast.py`).
- CTR Tracker: when a batch needed to insert *two* new rows for the same CTR number (its other currency, or another new revision), the two brand-new placeholder rows were indistinguishable to the write pass — both blank except for the CTR number — so it picked whichever came first regardless of which entry the insertion position was actually computed for, silently scrambling currency grouping and, worse, sometimes landing a new revision *before* an older one. `_plan_insertions` now simulates the cumulative shift every insertion in the batch causes on the others and gives each entry its exact final row up front; the write pass uses that directly instead of re-discovering a target. `ctr_generator/tracker_fast.py`.
- CTR Tracker: an entry with no revision value at all was never treated as matching an already-filled row's revision, even when that row's own revision was *also* blank — "same revision, so overwrite in place" only ever triggered when both sides had an actual value. A blank entry into an equally-blank row is now correctly treated as the same revision too, instead of being routed into spare/insert handling for no real reason; a blank entry into a row that *does* have a real revision is still correctly treated as different. `ctr_generator/tracker_fast.py`.
- CTR Tracker: fixed the ordering used to place a new "separate revision" row among a CTR's existing ones — revisions now compare as negative numbers, then blank ("no value"), then zero and positive numbers, in that order (e.g. "-1" < "" < "0" < "1"), instead of the previous rule, which pushed blank/non-numeric revisions after every numeric one regardless of sign. A revision like "Rev5" or "2-draft" is stripped down to its embedded number for this comparison only — the row's Revision column still gets the original text as typed, not the stripped number. `_revision_sort_key` (`ctr_generator/tracker_fast.py`).

Around ninety empty rows filled page one (printing as `###`), pushing equipment, consumables, the Summary and the CTR total onto page two; the exported PDF ran to three pages. Rows in those blocks that are genuinely empty across the printed columns are now contracted, which brings the whole document back onto page one and the PDF to two pages. Block boundaries live in `usd_template.main_unused_blocks`, and a template that does carry something there keeps showing it.
- Contracting unused rows now works in both directions, in every fixed-capacity block of both CTRs (AZN support + activities, USD equipment + consumables). The builders only ever *hid* leftover rows, never un-hid one — and since a template is made by saving a previous CTR, it arrives with that job's unused rows already hidden. Rows that have data are now explicitly expanded and only genuinely unused rows are contracted; a block filled to capacity has nothing to contract and is left alone. The stock template arrives with the "Consumables & Materials" heading hidden (a previous CTR was saved that way), so the consumables table printed with no title above it while every row around it showed.

On a CTR with transport lines the "Estimated CTR Total" line and the entire signature block were simply absent (135 text items rendered instead of 150). The print area now follows the inserted rows on all three sheets; the USD Pricing sheet's internal margin block stays outside it, as the template intends.

It normally goes unnoticed because column H is hidden and those Pricing rows fall outside the print area, but two of the "aa" cells sit in a visible column inside the print area and printed just below "Total Plant & Equipment", and all of the "AA" cells surface the moment a template is saved with column H shown. Only cells whose entire value is one of `placeholder_texts` are cleared, so the mirror formulas and real labels sharing those columns are untouched.
- USD CTR: the Pricing sheet's own header block (client, sub-client, CTR ref, location, date, revision, scope) is now written — each cell a formula mirroring its Main-sheet equivalent. - Generating into a template whose layout has been re-merged by hand no longer fails with `'MergedCell' object attribute 'value' is read-only`. openpyxl represents every cell of a merged range except its top-left as a read-only `MergedCell`, so any cell this code addresses by fixed position could crash the run once someone merged across it. Every fixed-address write now resolves through the merge and writes to the range's anchor — where the value visibly lands anyway; the bulk section writes skip non-anchor slots instead, since the anchor of a merge inside a block is visited by the loop in its own right.
